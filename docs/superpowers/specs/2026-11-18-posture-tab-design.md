# ダッシュボード「態勢」タブ 設計書

作成日: 2026-11-18 / 状態: 承認待ち

## 1. 意図と理由
バックエンドには、GitHub のセキュリティアラート（`/api/github-alerts`）・リポジトリ設定の監査
（`/api/repo-audit`）・公開サイトの外形監視（`/api/site-monitor`）の API があるが、**画面が無い**。
見るには、API や MCP を直接呼ぶ必要がある。2026-11-18 に CodeQL・シークレットスキャン・push protection
を有効にしたため、その結果（アラート）も同じ経路（`/api/github-alerts`）に入る。
これらを、既存の KEV / OSV / DEPSCAN / CODESCAN と同じダッシュボードで見られるようにする。

## 2. ゴール / 非ゴール / アンチゴール
**ゴール**
- 新タブ「態勢」を1つ足し、3つの情報（アラート・設定の監査・外形監視）を、1画面で見られる。
- 設定の抜けを、リポジトリをまたいで1画面で見つけられる（リポジトリ × 点検項目のマトリクス）。
- オブジェクト指向（責務ごとのクラス）で作り、**文言・配色・件数・パスを、コンポーネントに直書きしない**。

**非ゴール（今回やらない）**
- 全体の概要タブ（案C）。
- 既存の DEPSCAN / CODESCAN のログインゲートを、共通部品に置き換える（重複は、新規に増やさない。移行は後続）。
- アラートの解決・例外登録（閲覧のみ）。
- VM（OCI）の運用面の表示。

**アンチゴール（動いても失敗）**
- 数字を大きく見せるだけで、「どこを直すか」が分からない画面。
- 色だけで状態を伝える画面（色覚・モノクロで読めない）。
- シークレットの値・コードの断片を、画面に出すこと（API も返さない）。

## 3. 制約
- 既存の技術: React + TypeScript + Tailwind + lucide-react + Vitest + Playwright（E2E。API 全モック）。
- 既存の規約: 新しいタブは `components/layout/tabs.tsx` に1件足す。API クライアントは `api/` に置き、`client.ts` で
  re-export。設定値は `freshnessConfig.ts` のように1か所に置く（環境変数で上書き可）。
- E2E のシナリオ網羅率90%を保つ（`e2e/support/scenarios.ts` に追加し、対応するテストを書く）。
- CSP の変更なし（同じ API のオリジン）。外部データの URL は `safeHttpUrl` で http(s) のみリンク化する。
- 認証: 3つの API は `require_api_key_or_session`。画面は DEPSCAN と同じ GitHub ログインを使い、本人所有のリポジトリだけを見る。
- 行数: README・docs の分割ファイルは200行以内、スキルは500行以内、CLAUDE.md は200行以内（現在ちょうど200）。

## 4. 案
| 案 | 内容 | 結論 |
|---|---|---|
| **A. 新タブ「態勢」** | 3つを1つの新タブにまとめる。API は既存 | **採用**。既存タブに触れず、画面だけで完結 |
| B. 既存タブに混ぜる | コード系を CODESCAN、Dependabot を DEPSCAN に入れる | 出どころ（別テーブル）が違い、一覧が複雑になる |
| C. 概要タブ | 全領域の「今対応が必要なもの」 | 大きい。A の部品を使って、後で足せる |

## 5. 設計
### 5.1 全体の構成（責務の分離）
```
api/posture.ts                取得だけ（型・URL・クエリ）。client.ts で re-export
components/posture/
  postureConfig.ts            文言・配色・種類・重要度の順位・件数。1か所だけに置く（環境変数で上書き可）
  model/                      ドメインのクラス（画面を知らない。単体テストできる）
  usePostureData.ts           3つの取得を並行に行い、1つずつ失敗を許す（取得状態を持つ）
  PostureAuthGate.tsx         ログインゲート（共通部品 shared/GithubLoginGate を使う）
  PosturePanel.tsx            組み立てのみ
  PostureSummaryBand.tsx / AuditMatrixSection.tsx / AlertsSection.tsx / SiteMonitorSection.tsx
```

### 5.2 クラス（オブジェクト指向）
継承は使わず、小さな不変クラスの**合成**で作る（Composition over Inheritance）。各クラスは、API の生データを受け取り、
自分の判断（集計・並べ替え・絞り込み）を、自分のメソッドで行う（Tell, Don't Ask）。画面は、結果を描くだけ。

| クラス | 責務 |
|---|---|
| `AuditStatus` | API の状態（ok / ng / それ以外）を、安全に読み取る値オブジェクト。未知の値は「取得不可」に倒す |
| `AuditCheck` | 点検項目1件（キー・**ラベル（API が返す）**・状態・重み・詳細・直し方） |
| `RepoAudit` | 1リポジトリの点検結果。`checkOf(key)`・スコア・改善件数 |
| `AuditMatrix` | 複数の `RepoAudit`。**列は、API が返す項目から導く**（項目名を直書きしない）。並べ替え・検索・「改善が必要なものだけ」 |
| `AlertKind` | アラートの種類（secret / dependabot / code）の表示情報。`postureConfig` から作る |
| `GithubAlert` / `AlertList` | アラート1件と、その集合。種類・重要度・リポジトリで絞る。重要度の順位は設定から |
| `SiteCheck` | 外形監視1件。最悪の指摘の重要度を返す。**判定のしきい値は、バックエンドの指摘（`findings`）に従い、画面で再計算しない** |
| `PostureSummary` | 3つを束ねた、見出しの数値（未対応アラート・設定の達成率・外形監視の異常）。取得できなかった源は「不明」と表す |

### 5.3 ハードコードを避ける
- **文言・配色・順位は `postureConfig.ts` のみ**（状態→表示、種類→ラベル・アイコン、重要度→順位・クラス）。
- **点検項目の名前・直し方は、API が返す値を使う**（`label`・`fix`）。画面に項目名の一覧を持たない。
- API のパス・既定の件数は、定数にして1か所に置く（`PER_PAGE` などは `numberFromEnv` で環境変数から上書き可）。
- 日時の表示は、既存の `DISPLAY_LOCALE` を使う。

### 5.4 画面
```
態勢                                  最終取得: 〜
[ 未対応アラート 12 ] [ 設定の達成率 78% ] [ 外形監視の異常 0 ]   ← StatBand（既存部品）

リポジトリ × 点検項目            [改善が必要なものだけ ✓] [検索]  [運用状態 ▾]
                  項目A  項目B  項目C  …           ← 列は API の項目から
 cyberattack_info   ✓      ✓      ✓
 baby_vehicles      ✕      ✕      ✓
 todo-app           ✓      －     ✓                  ✓ 合格 / ✕ 不合格 / － 取得不可
 （セルを押す → その場で、詳細と直し方を表示）

アラート    種類 [すべて ▾]  重要度 [すべて ▾]
 重要度  種類   リポジトリ   タイトル            検知元
 HIGH   コード  …           …                 CodeQL ↗
 取得できなかった項目（機能が無効・権限不足）は、一覧の下に、理由つきで出す

外形監視    URL / 取得元 / TLS 残日数 / 指摘
```
- **見せ場は、マトリクス1か所**。ほかは、既存の CODESCAN と同じ表の作りにそろえる。
- **色だけに頼らない**: 状態は、記号（✓ ✕ －）と色の両方で示す。セルは、ボタンで、名前に「リポジトリ・項目・状態」を含める。
- スマホ幅: マトリクスは横スクロールし、リポジトリ名の列を固定する。
- 自動の動きは、つけない。セルを開く動きは、操作への応答だけ。
- 3つの取得は、**独立**。1つ失敗しても、ほかは表示し、失敗した部分に原因と再試行を出す。

### 5.5 テスト
- クラスは、Vitest で単体テスト（未知の状態・空・取得不可・並べ替え・重要度の順位）。
- 画面は、コンポーネントのテスト。
- E2E: シナリオ `POS-01…` を `scenarios.ts` に足し、`mockApi.ts`・`mockData.ts` に3つの API を足す。
  既存の「4つのタブ」のシナリオ（APP-02）は5つに直す。

### 5.6 ドキュメント
`dashboard-frontend` スキル・README・CLAUDE.md（「4タブ」→「5タブ」。**1行の中で直す**）・docs を、実装のPRで更新する。

## 6. 私の判断（承認時に、確認してください）
1. **新しいクラスは `components/posture/model/` に置く**（既存の `components/<機能>/` の規約に合わせる）。
2. **ログインゲートは、共通部品 `shared/GithubLoginGate` を新設し、新タブだけが使う**（3つ目のコピーを作らない）。
3. **タブの見出しの「最終取得」は、3つのクローラー（GHALERT・REPOAUDIT・EXTMON）に対応させる**。
   `FetchedCrawlerType` に3種を足し、各セクションに、それぞれの最終取得を出す（タブ全体の見出しは、いちばん古いもの）。
4. **運用停止中のアプリの扱い（要確認）**: DEPSCAN には「運用状態」の絞り込み（`operating`）があるが、この3つの API には無い。
   運用停止中のアプリが122件あるため、そのままでは、マトリクスが、ほぼ停止中のアプリで埋まる。
   **既存の `core/findings/operating_status` を使い、3つの API に `operating` を足す**（バックエンドの小さな変更）。
